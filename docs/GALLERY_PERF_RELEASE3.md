# Галерея, Реліз 3: заміри

Усе виміряно 7 листопада 2026 року в Chromium із Playwright (емуляція iPhone 13 і десктопа 1280×800),
на production-збірці (`next build && next start`) з демо-галереєю `/uk/gallery-demo`.

## 1. Сітка до гідрації (серверний фолбек)

**Що змінилося.** Раніше `GalleryGrid` до гідрації рендерив порожнє місце на 100vh: плитки
з'являлися лише після завантаження й запуску JS. Тепер сервер віддає перші 24 плитки чистим CSS:
- квадрат / портрет / колаж / редакційна — CSS-сітка з тими самими класами, колонки за
  брейкпоінтами через `@media`;
- masonry — флекс-колонки, окремий блок для кожної кількості колонок (телефон / планшет / десктоп),
  видимий лише свій через `@media`. Колонку для кожного фото вибирає `assignMasonryLanes` лише з
  пропорцій, тож на сервері й у браузері фото лягають в ту саму колонку;
- кожна плитка має `aspect-ratio` з `width/height` асету й сіру заглушку, поки фото вантажиться;
- перші 6 плиток `loading="eager"`, решта `lazy`; `src` + `srcset` + `sizes` однакові на сервері й
  після гідрації (`sizes` рахується з розкладки, а не з виміряної ширини), тож браузер нічого не
  вантажить двічі.

Після гідрації, ще до першого кадру, ту саму розкладку замінює віртуальна сітка. Плитки, що є в обох,
стоять на тих самих місцях (перевірено скриптом: усі збігаються до 1 px) і мають ті самі URL.

**Цифри** (медіана з 3 прогонів; «повільний 4G» = 150 мс RTT, 1,6 Мбіт/с, CPU 4x, 1 прогін):

| | до | після |
|---|---|---|
| CLS, десктоп (усі розкладки, класична й «Мінімал») | 0,0002 | 0,002–0,003 |
| CLS, iPhone 13 | 0,0000 | 0,0000–0,0019 |
| Перша плитка в DOM, CPU 4x, локально | 370–550 мс (після JS) | одразу в HTML |
| Перша плитка в DOM, повільний 4G | 2,6–3,2 с | одразу в HTML |
| LCP, «Мінімал», повільний 4G | 7,3–8,0 с | ≈0,5 с |
| LCP, класична обкладинка, повільний 4G | ≈3,5 с | ≈0,5 с |

CLS «до» майже нульовий, бо порожнє місце, яке згодом заповнюється, зсувом не вважається;
проблемою була порожнеча, а не зсув. Зсув 0,002 «після» — це не сітка: за `LayoutShift.sources` це
текст і кнопки обкладинки й липкої панелі, коли довантажуються шрифти. Серед джерел немає жодної
плитки.

Тести: `tests/e2e/grid-ssr.spec.ts` (без JS видно плитки; CLS < 0,05 на iPhone 13 і десктопі;
жодне зображення не вантажиться двічі).

## 2. Вартість третього варіанта (`mobile`, WebP 1080 px) при завантаженні

**Як міряли.** Ізольований стенд: справжній `uploadFileToGallery` з цього релізу («після») і з
`release/2` («до»), той самий пул із 5 паралельних завантажень, що в `Uploader.tsx`; локальний
сервер приймає presign / PUT / complete. 50 JPEG по 24 Мп (6000×4000), 9–17,5 МБ, разом 668 МБ.
Інтерфейс: проміжки між кадрами (`requestAnimationFrame`), довгі задачі (`longtask`), проміжки
між оновленнями прогресу.

| сценарій | до | після | різниця |
|---|---|---|---|
| без обмеження мережі, CPU 1x | 4,9 с | 6,0 с | +1,1 с (+23 %) |
| без обмеження мережі, CPU 4x | 15,0 с | 17,3 с | +2,3 с (+15 %) |
| мережа 100 Мбіт/с, CPU 1x | 56,1 с | 56,7 с | +0,6 с (+1 %) |
| мережа 100 Мбіт/с, CPU 4x | 56,2 с | 56,8 с | +0,6 с (+1 %) |
| відвантажено даних | 698 МБ | 705 МБ | +7 МБ (≈140 КБ на фото) |

Без обмеження мережі видно чисту ціну CPU. З реальною мережею кодування йде паралельно з
відвантаженням оригіналу, і додатковий час майже зникає.

**Чи блокується інтерфейс.**
- CPU 1x: довгих задач немає (0–2 за весь прогін), кадри рівно по 17 мс, прогрес оновлюється
  щонайменше раз на ~0,3 с.
- CPU 4x: по одній довгій задачі ~100 мс на файл, **так само й до змін** (50 «до», 50 «після»).
  Це синхронна частина `canvas.toBlob` для прев'ю 2048 px (~70 мс) плюс `drawImage` (~20 мс).
  Новий WebP додає окрему коротку задачу ~30 мс (нижче порогу 50 мс), нових довгих задач немає.
  95-й перцентиль кадру однаковий (67 мс без мережі, 17 мс із мережею), найдовший кадр 150–167 →
  183–200 мс. Вкладка не «зависає», прогрес-бар оновлюється.

Тому кодування **не винесене** у Web Worker. Якщо колись знадобиться прибрати й наявні
~100 мс довгі задачі на повільних ноутбуках, рецепт такий: `createImageBitmap` + `OffscreenCanvas`
+ `convertToBlob` у воркері з фолбеком на поточний шлях. Ризик: поворот за EXIF
(`imageOrientation`) і WebP у Safari треба перевіряти окремо.
