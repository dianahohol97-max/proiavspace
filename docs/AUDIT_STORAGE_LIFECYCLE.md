## 1. Карта реалізації

### Блок 1.1. Ліміт сховища

**Як рахується.** Рахується за метаданими в БД, а не за вмістом бакета. `profiles.storage_used_bytes` міняє тригер `apply_storage_delta` на `INSERT/DELETE` у двох таблицях:
- `assets` (`supabase/migrations/0001_phase1_galleries.sql:150-176`);
- `portfolio_assets` (`0009_portfolio_pricing.sql:30`).

Рахується лише оригінал. Прев'ю, тумби й постери не входять (`src/lib/uploads.ts:190-193`).

**Прод зараз.** Два профілі. Розбіжності між лічильником і сумою `assets + portfolio_assets` немає: 169 МБ, з яких 162 МБ — портфоліо сайту.

**Де стоїть перевірка**

| Шар | Файл | Що перевіряє | На чому |
|---|---|---|---|
| Клієнт | `src/components/Uploader.tsx`, `src/lib/upload/client.ts` | лише показує помилку сервера | — |
| API presign | `src/app/api/uploads/presign/route.ts` → `authorizeUpload` (`src/lib/uploads.ts:21-66`) | тип, ≤ 2 ГБ, власник галереї, відео за тарифом, `used + size ≤ min(limit, ліміт ефективного тарифу)` | **розмір, заявлений клієнтом** |
| API multipart create | `src/app/api/uploads/multipart/create/route.ts` | те саме | заявлений розмір |
| API part-urls | `.../multipart/part-urls/route.ts` | лише префікс ключа; до 1000 URL за запит, без ліміту кількості запитів | — |
| API complete | `src/app/api/uploads/complete/route.ts`, `.../multipart/complete/route.ts` → `registerAsset` (`src/lib/uploads.ts:112-213`) | робить HEAD у B2 і повторно проганяє `authorizeUpload` на **фактичному** розмірі й типі. Якщо не проходить — видаляє об'єкт | фактичний розмір |
| Імпорт zip | `src/app/api/import/start/route.ts:183-203` | весь zip має влізти заздалегідь (порада; справжній гейт — `complete`) | заявлені розміри |
| БД | тригер | **лише рахує, ліміт не перевіряє** | — |

**Сценарії.** Усі покриті тестами, див. розділ 3.

| Сценарій | Результат |
|---|---|
| «Базовий», 99,9 ГБ + 200 МБ | presign → 403 `storage_quota_exceeded` ✅ |
| Presign «1 МБ», у B2 залито 5 ГБ, викликано `complete` | HEAD бачить 5 ГБ → 403, об'єкт видалено, місце не змінилось ✅ |
| Те саме, але `complete` не викликано | ❌ **ST-02.** URL підписує лише `host` (`X-Amz-SignedHeaders=host`), тож PUT будь-якого розміру до 5 ГБ приймається. Об'єкт лежить під `u/<uid>/g/<gid>/o/…` і не рахується. Прибирає його лише `deleteGallery` (list префікса), крону немає. Presign живе 10 хв, кількість presign не обмежена |
| Кілька вкладок разом перевищують ліміт | ❌ **ST-01.** 99,9 ГБ + 5 × 60 МБ паралельно → 100,19 ГБ. Кожен `complete` читає старе `used`. БД вставку понад ліміт теж пропускає |
| Повторна відправка того самого файлу | Кожен presign дає новий UUID-ключ, тому це 2 об'єкти й 2 рядки, місце рахується двічі. Це не витік: фотограф бачить дубль і може його видалити. Для zip-імпорту дубль по `original_name` дає 409, а другий об'єкт видаляється ✅ |
| Невдале завантаження (PUT обірвався, об'єкта нема) | `complete` → 400 `upload_missing`, місце не змінюється ✅. Частково залитий multipart лишається в B2 як незавершений (ST-03) |
| Multipart | `abort` викликається лише з браузера. Коментар у `multipart/abort/route.ts:26-29` посилається на авто-очищення R2, а прод на **B2** (`STORAGE_PROVIDER` — див. Vercel env). Незавершені великі файли в B2 тарифікуються, поки їх не скасувати (ST-03) |

**Висновок щодо «101-й ГБ неможливий жодним шляхом»: не виконується.** Обхід паралельністю обмежений кількістю вкладок × 2 ГБ. Обхід через «presign без `complete`» не обмежений нічим.

### Блок 1.2. Даунгрейд і кінець тарифу

**Як це влаштовано.** Стан тарифу зберігають `profiles.plan`, `profiles.storage_limit_bytes` і `profiles.grace_until`. Реально діючий тариф рахується «ліниво» функцією `effectiveGalleryPlan` (`src/lib/plans.ts:175-185`): якщо `grace_until` минув, акаунт поводиться як Free. При цьому `plan` і `storage_limit_bytes` у профілі лишаються старими.

Хто виставляє `grace_until`:

| Подія | Де | `grace_until` |
|---|---|---|
| Оплата з карткою (автопродовження) | `api/billing/webhook/route.ts:194-205` | `null` |
| Оплата без токена картки | там само, `paidUntil` | кінець періоду + 7 днів |
| Скасування підписки | `api/billing/subscription/cancel/route.ts:53-60` | `next_charge_at` + 7 днів |
| Невдале автосписання | `api/billing/renew/route.ts:63-84`, webhook `:266-285` | зараз + 7 днів, статус `past_due` (повторних спроб немає) |
| Промо імпорту | `grant_import_promo`, `0038_import_promo.sql:70-110` | кінець промо-місяця (без +7) |
| Ручний даунгрейд на нижчий тариф | **не існує.** Є лише «купити інший тариф»: webhook ставить новий `plan` і ліміт одразу | — |
| Повернення на Free | окремої дії немає; відбувається, коли минає grace | — |

**Стани після того, як grace минув** (включно з кінцем промо й переходом на тариф із меншим лімітом):

| Що | Стан |
|---|---|
| Галереї для клієнта | **відкриті як були.** `g/[slug]/page.tsx` тариф не перевіряє, крім оформлення. Повертається бейдж «проЯв», зникають лого фотографа й посилання на чайові. Відео, що вже завантажені, **грають далі**. Оригінали й архів качаються |
| Закриття галереї | лише з `galleries.expires_at`, яке ставить сам фотограф (RLS: «published, non-expired») |
| Нові завантаження | блокуються, поки `used > ліміт Free`; відео — завжди |
| Файли в B2 | **лишаються безстроково.** Коду, що видаляє файли за станом тарифу, немає. Крон один — `/api/billing/renew` (`vercel.json`), і він файли не чіпає |
| Рядки в БД | `past_due`-підписка лишається назавжди; скасовані видаляються кроном |

**Відповідь на критичне питання: так.** Будь-який акаунт, який колись мав платний тариф або промо, може безстроково зберігати до 100 ГБ / 500 ГБ / 1 ТБ у B2 за наш рахунок. Для цього досить завантажити файли й не платити. Промо відкрите для будь-якого Free-акаунта з одним фото в zip, тож 30 × 100 ГБ = 3 ТБ ≈ $18/міс у B2 назавжди. Так само не видаляються файли видалених акаунтів (4.1).

### Блок 1.5. Промо, реферальний кредит, річна оплата

**Механіка:**
- Промо видає `grant_import_promo` (атомарно, з advisory lock) з `api/import/finish/route.ts:108-121`.
- Кредит списується в `api/billing/checkout/route.ts:128-147`. Поки йде промо, він **не** застосовується.
- `promo_autopay` зсуває початок оплаченого періоду на кінець промо (`webhook/route.ts:146-163`).

| Сценарій | Що відбувається |
|---|---|
| Імпорт → промо-місяць → річна оплата | Звичайний checkout з `period=year` під час промо стартує рік **від сьогодні**, решта промо згорає. `promo_autopay` дозволяє лише місяць (`checkout/route.ts:61-62`). Двох безкоштовних періодів тут не виникає, але користувач втрачає залишок промо (PR-03) |
| Імпорт двічі з одного акаунта | вдруге промо не дається: PK `user_id` у `promo_grants` + перевірка ✅ (тест) |
| Імпорт після платного тарифу | під час дії тарифу або grace — **ні** ✅. Коли grace минув — **так**, колишній платник знову отримує безкоштовний місяць (PR-02: рішення за тобою) |
| Промо-місяць + кредит на першу оплату після нього | Під час промо кредит не списується. Після кінця промо звичайний checkout списує кредит аж до «мінімум 1 ₴». Тобто при кредиті ≥ 128 ₴ другий місяць «Базового» коштує 1 ₴ — **фактично два безкоштовні місяці підряд**. Так працює кредит; якщо небажано — обмеж частку знижки |
| Чи рахується промо як «оплата» для рефералів | **Ні** ✅. Промо не створює рядок у `payments`, `referrals.status` лишається `pending`, `referral_earnings` порожня (тест на БД). Оплата `promo_autopay` — справжня, тож 10% з неї нараховуються. Це правильно |
| Лічильник «перші 30» | `count(*) from promo_grants` під advisory lock — гонки немає ✅, N+1-й не отримує ✅ (тест). ❌ **PR-01:** рядок видаляється каскадом при видаленні акаунта з Auth, тож слот звільняється й загалом можна роздати понад 30 |
| Дедлайн | `2027-01-01T00:00:00+02:00` = 31.12.2026 включно за Києвом ✅ |
| Зайвий шлях | `pending_free_months` у `renew/route.ts:246-264` ніщо не нараховує (лише колонка з `0023`). Мертвий код, у скоуп рефералів |

### Блок 4. Дані й довіра

**4.1. Видалення акаунта**
- У кабінеті **шляху немає** (немає `deleteUser` і сторінки). Оферта обіцяє «дані видаляються… у розумний строк» (`legal/copy.ts:155`).
- Видалення через Supabase Auth напряму:
  - каскад прибирає `profiles`, `galleries`, `assets`, `portfolio_assets`, `promo_grants` і квоту (тест);
  - **файли в B2 лишаються сиротами назавжди** — ключі зникають разом із рядками (LC-02);
  - крону на сироти немає;
  - ❌ **для акаунта з рефералом видалення падає** на FK `referrals.referred_id` / `referrer_id` без `on delete` (LC-03, тест). У дашборді Supabase це виглядає як «Database error deleting user».

**4.2. Бекапи**
- **Supabase:** організація Proiav на плані **free** (перевірено API). На Free Supabase **не робить жодних бекапів** — ні щоденних, ні PITR ([документація](https://supabase.com/docs/guides/platform/backups)). Експорту метаданих галерей у застосунку немає.
- **B2:** налаштувань бакета я не бачу. Код ставить на версіонування: `DeleteObjects` без `VersionId` у B2 ховає файл, а не стирає (ST-04). Object Lock і реплікацію треба перевірити (команди в розділі 4). Плану на втрату бакета немає.

**4.3. Rate limit.** У застосунку **нічого** немає, крім глобальної стелі в `/api/debug-log`.
- Реєстрація, логін і magic link ідуть із браузера напряму в Supabase Auth. Діють лише вбудовані ліміти Supabase за IP, їх видно в Auth → Rate Limits. CAPTCHA не увімкнено (у коді немає `captchaToken`). Блокування одноразових email немає.
- Скидання пароля — шляху немає.
- Незахищені app-ендпоінти:
  - `/api/uploads/presign`, `/multipart/*` — авторизовано, без ліміту частоти;
  - `/api/galleries/*/unlock` — перебір пароля;
  - `/selections`, `/archive-urls` — публічні;
  - `/api/booking/book`, `/api/sites/lead` — публічні форми.

## 4. Ручний чек-лист для проду

### Блок 1. Сховище й тариф

Підготовка: тестовий акаунт `audit+1@…` і 3–4 файли. Відео на 50 МБ і 600 МБ, щоб піти через multipart.

1. **B2: налаштування бакета** (b2 CLI v4, ключ із правом `readBuckets`/`listFiles`):
   ```bash
   b2 account authorize                      # keyId / applicationKey
   b2 bucket get <B2_BUCKET>                 # bucketType, lifecycleRules, fileLockConfiguration, replication
   b2 ls -r --versions b2://<B2_BUCKET>/u/ | head -50          # приховані версії = платні «видалені» файли
   b2 file large unfinished list b2://<B2_BUCKET>              # незавершені multipart
   ```
   Очікую:
   - `bucketType: allPrivate`;
   - `lifecycleRules` з `daysFromHidingToDeleting` (1–30);
   - порожній список незавершених.

   Якщо `lifecycleRules: []` — кожне видалення в застосунку лишає платну приховану копію (ST-04).
2. **Чи бакет публічний:** візьми будь-який `r2_key` з `assets` і виконай `curl -sI https://f003.backblazeb2.com/file/<B2_BUCKET>/<r2_key>` (`f003` для `eu-central-003`). Очікую `401`/`403`. `200` означає, що оригінали доступні за ключем без підпису.
3. **Ліміт, UI:** на «Базовому» (або тимчасово виставленому через SQL `storage_limit_bytes` = used + 100 МБ) завантаж файл на 150 МБ. Очікую червону помилку «місце закінчилось», а `storage_used_bytes` без змін.
4. **Паралельні вкладки:** той самий акаунт із запасом 100 МБ, три вкладки, у кожній файл на 60 МБ одночасно. Зараз ліміт буде перевищено (ST-01). Зафіксуй `storage_used_bytes` до й після.
5. **Обхід presign:** у DevTools скопіюй відповідь `/api/uploads/presign` для файлу на 1 МБ і зроби `curl -X PUT -H 'Content-Type: image/jpeg' --data-binary @/dev/zero …` на 50 МБ (`head -c 50M /dev/zero > z`). Очікувано (баг): `200`. Потім `b2 ls` покаже об'єкт, якого немає в `assets`. Прибери його руками.
6. **Обірване завантаження:** почни відео на 600 МБ і закрий вкладку на 30%. `b2 file large unfinished list` покаже незавершений файл (ST-03). Скасуй: `b2 file large unfinished cancel b2://<bucket>/<key>`.
7. **Відео на Free:** Free-акаунт → завантаж mp4. Очікую повідомлення «Відео доступне з «Базового»» і посилання на тарифи; zip з mp4 → звіт «пропущено відео: N».
8. **Grace:** тестовий акаунт на «Базовому» → у SQL `update profiles set grace_until = now() - interval '1 minute'`. Кабінет має показати ліміт Free, завантаження блокуються, публічна галерея — з бейджем, без лого. `b2 ls` — файли на місці.
9. **Промо:** новий Free-акаунт → імпорт zip з 1 фото. Очікую:
   - звіт «нараховано місяць Базового до …»;
   - `promo_grants` +1;
   - `payments` без нових рядків;
   - повторний імпорт — без промо.
   Далі перевір `select count(*) from promo_grants` (має бути ≤ 30).
10. **Скасування:** оплати «Базовий» тестовою карткою Monobank, скасуй підписку. Очікую `grace_until` = `next_charge_at` + 7 днів, а картку видалено (у кабінеті Monobank).

### Блок 3. Клієнт

Підготовка: галерея на ~2 500 фото (або на 300 для швидкості), з паролем і з відео.

1. **Пароль:**
   - неправильний → помилка;
   - правильний → галерея;
   - у приватному вікні відкрий `/api/assets/<id>/download` → `403 locked`;
   - постав новий пароль → старе вікно **досі бачить галерею** (CL-05).
2. **Перебір:** `for i in $(seq 1 50); do curl -s -o /dev/null -w '%{http_code}\n' -X POST -F password=x$i -F locale=uk https://proiav.space/api/galleries/<slug>/unlock; done`. Зараз усі 50 проходять (303), жодного `429` (RL-01).
3. **Прямі посилання:** скопіюй `src` будь-якого прев'ю, відкрий через 61 хв → очікую `403` (presigned на 1 год). Оригінал із download — живе 5 хв.
4. **Архів, Chrome на десктопі:** «Завантажити все» → діалог збереження → zip. Відкрий у Finder або Провіднику і в `unzip -t`. Галерея **> 4 ГБ** — очікувано (баг CL-01) «архів пошкоджено».
5. **Архів, Safari / Firefox / iPhone / Android:** на галереї 2–3 ГБ стеж за пам'яттю вкладки (Safari → Develop → Timelines). Очікувано (баг CL-02): вкладка падає або перезавантажується.
6. **Архів, повільна мережа:** DevTools → Network → «Fast 4G», галерея на 500+ фото. Через 15 хв запити почнуть отримувати `403` (CL-03).
7. **Трафік:** під час архіву в DevTools перевір, що запити йдуть на `s3.eu-central-003.backblazeb2.com`, а не на `proiav.space`. Через 1–2 дні зайди у Vercel → Usage і переконайся, що Fast Data Transfer не виріс на обсяг архіву.
8. **Лайки:** постав 5 сердечок, онови сторінку — збережено. У кабінеті фотографа видно 5 і «1 людина». В іншому браузері — порожньо, це окремий клієнт.
9. **Слайдшоу:** ▶ → повний екран, стрілки, пауза, вихід Esc; на телефоні — свайпи.
10. **Мобільний перегляд 2–3 тис. фото:** iPhone SE / бюджетний Android. Заміряй час до першого кадру, плавність скролу до кінця, пам'ять. У Lighthouse (mobile) — розмір HTML-документа: очікую 2–4 МБ (CL-06).
11. **Тариф фотографа закінчився:** крок 8 з блоку 1, потім відкрий галерею як клієнт. Бейдж «проЯв», немає лого, решта працює.

**Rate limit — мінімум і вартість**

1. **Supabase Auth (0 грн):**
   - увімкнути CAPTCHA (Cloudflare Turnstile безкоштовний) для sign-up / sign-in / OTP і передавати `captchaToken` з `login/page.tsx`;
   - перевірити Auth → Rate Limits;
   - одноразові email — Auth Hook «before user created» зі списком доменів (open-source список `disposable-email-domains`).
2. **Vercel Firewall (без коду):** правила rate limit за IP для `/api/galleries/*/unlock` (10/хв), `/api/uploads/*` (300/хв), `/api/booking/book` і `/api/sites/lead` (5/хв). Доступність і ліміти правил залежать від плану Vercel — перевір Project → Firewall → Rules. На Pro ($20/міс) rate limiting є; на Hobby — обмежено, і Hobby не дозволяє комерційне використання. План команди через API я не побачила, перевір у Settings → Billing.
3. **Upstash Redis + `@upstash/ratelimit` у route handlers (per-user для presign, per-IP+slug для unlock):** безкоштовний тариф покриває цей масштаб; далі pay-as-you-go, центи на місяць. Middleware для цього не потрібен: ліміт ставиться лише на кілька маршрутів.

**Бекапи — рекомендації з вартістю**
- **БД:**
  - нічний `pg_dump` з GitHub Actions у бакет B2 `proiav-backups` з Object Lock (governance, 30 днів) — ≈ $0 (дамп — мегабайти). Потрібен секрет `SUPABASE_DB_URL`;
  - Supabase Pro — $25/міс, щоденні бекапи 7 днів.
- **Метадані галерей:** той самий дамп їх покриває. Окремий «експорт галерей» для фотографа (CSV або JSON з назвами файлів і вибором) — фіча, не бекап.
- **B2:**
  - lifecycle `daysFromHidingToDeleting: 7` як кошик — +вартість 7 днів «видаленого»;
  - Cloud Replication в інший регіон — ×2 вартості зберігання (1 ТБ → +$6/міс). Варто вмикати, коли даних стане > 1 ТБ або з'являться платні клієнти;
  - Object Lock на основному бакеті **не** вмикати: він зламає видалення з кабінету;
  - план на втрату бакета: реплікація + скрипт відновлення ключів з дампу БД.
