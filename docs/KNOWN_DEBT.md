## Галерея: дозавантажені фото не стають на своє місце за часом зйомки

*Записано 07.11.2026 · статус: відкладено (після `feat/gallery-grid`, міграція `0067`)*

**Що є** «Порядок: за часом зйомки» в кабінеті — одноразова дія: `sort_gallery_assets`
переписує `assets.position` (1..n) за `taken_at`. Звичайне завантаження потім
пише нове фото з `position = 0` (дефолт), тож у галереї (порядок
`position, created_at`) дозавантажені кадри опиняються **на початку**, а не між
сусідами за часом. Так само поводиться дозавантаження після імпорту zip.
Зараз фотографові треба натиснути «За часом зйомки» ще раз.

**Чому не зараз** Потрібне рішення, де зберігати вибраний порядок галереї
(колонка `galleries.sort_mode` чи поле в `galleries.style`), і нова міграція;
поза межами задачі «Рядки / EXIF / HEIC».

**Що зробити** Зберігати режим порядку галереї; коли він «за часом зйомки»,
`registerAsset` (`src/lib/uploads.ts`) ставить нове фото на місце за `taken_at`
(або після реєстрації партії викликає `sort_gallery_assets`). Фото без дати —
у кінець, як і зараз. Покрити тестом у `tests/audit-storage/gallery-grid.test.ts`
і на локальному Postgres.

## Публічні RPC без обмеження частоти: заявки, бронювання, лічильники

*Записано 07.11.2026 · статус: відкладено, не в межах `0060`*

**Що є** Ці SECURITY DEFINER функції навмисно доступні `anon` (з них працюють
сайт, бронювання й публічна галерея), але в базі немає жодного обмеження частоти:

- `record_site_lead` — форма заявки на сайті фотографа: можна засипати
  фотографа спамом (і листами, якщо на заявку йде сповіщення);
- `book_slot` — бронь слота: бот може за хвилину зайняти всі вільні слоти
  вигаданими контактами (слоти з ціною звільняться лише через
  `unpaid_release_hours`, безкоштовні — ніколи);
- `record_gallery_view`, `record_photo_view`, `record_gallery_download`,
  `record_gallery_archive` — лічильники: накрутка статистики фотографа
  (лише для опублікованих галерей).

**Чому не зараз** Окрема задача з власним дизайном: де рахувати (таблиця в БД
за IP/токеном, Vercel Firewall, Cloudflare перед API), які ліміти, що
бачить клієнт при спрацюванні. Попередження Supabase для цих функцій
лишаються свідомо.

**Що зробити** Вибрати місце для ліміту, почати з `book_slot` і
`record_site_lead` (реальна шкода), лічильники — згодом.

## Supabase: захист від злитих паролів вимкнено (відкрите питання)

*Записано 07.11.2026 · статус: відкрите питання, міграцією не закривається*

**Що є** Supabase Security Advisor: «Leaked Password Protection Disabled»
(`auth_leaked_password_protection`). Перевірка паролів через HaveIBeenPwned
вмикається в Authentication → Providers → Email → Password security, але
доступна лише на тарифі **Pro**, а проєкт зараз не на ньому.

**Питання** Переходимо на Pro (тоді просто увімкнути перемикач) чи лишаємо як
є? Попередження в Advisor лишається до рішення.

## LCP сайтів фотографів ~3 с (ціль 2,5 с) — для всіх тем

*Записано 07.11.2026 · статус: окрема задача, не в межах тем*

**Що є** Lighthouse mobile на демо «Тиші» й «Опівночі»: 92–98 балів, CLS 0,
TBT 20–80 мс, але LCP (симуляція Lighthouse) 2,4–3,2 с, FCP ~1,4 с. Реальний
LCP на тих самих сторінках — 0,2–0,3 с.

**Чому не в темах** Перевірено: блокування всіх кадрів нижче першого екрана
й полегшення hero (AVIF 38 → 27 КБ) LCP не змінюють. Hero вже серверний
`<img fetchpriority=high>` з AVIF/WebP і `mobile`-варіантом, шрифт — один
файл із preload. Решта — спільна база сторінок сайтів: HTML з RSC-пейлоадом
(~20 КБ gzip), CSS усіх тем в одному бандлі (~22 КБ gzip, бо SiteRenderer
імпортує всі теми), Manrope (2 файли) і JS Next/React (~110 КБ), які
стартують до LCP і потрапляють у граф симуляції.

**Що спробувати (окремий PR)** Розділити CSS тем по маршрутах (тема — окремий
сегмент або динамічний імпорт з CSS), скоротити RSC-пейлоад публічних сайтів,
subset Manrope під текст сайту, переглянути, які клієнтські чанки потрібні до
гідрації першого екрана. Міряти 3 прогони, як у звітах тем.

## Brevo: «Authorized IPs» має бути вимкнено для SMTP

*Записано 27.09.2026 · статус: налаштування, стежити*

**Що трапляється** Supabase Auth шле листи (підтвердження, magic link, скидання
пароля) через Custom SMTP Brevo з динамічних IP Supabase. Якщо в Brevo →
**Security → Authorized IPs** увімкнено обмеження, Brevo відповідає
`525 Unauthorized IP`, Supabase — 500 «Error sending confirmation email», і
реєстрація «мовчки» падає: акаунт у `auth.users` створюється, листа немає.
До PR 2 сторінка `/login` ще й показувала на це «пошта вже зайнята».

**Що зроблено** Authorized IPs вимкнено для SMTP. `/login` тепер розрізняє
«пошта зареєстрована» / «не вдалося надіслати лист» / інше
(`src/lib/auth-errors.ts`).

**Як перевірити** Supabase → Logs → Auth: немає `525`; реєстрація нової
пошти → лист приходить. Якщо колись знадобиться allowlist IP у Brevo для API
(`BREVO_API_KEY` з Vercel), — **не** поширювати його на SMTP: IP Supabase не
фіксовані.

## Покинутий інвойс Monobank: webhook для `expired` не приходить

*Записано 26.09.2026 · статус: закрито обхідним шляхом, стежити*

**Факт з документації** (`api.monobank.ua/docs/acquiring.html`, `invoice/create` →
`webHookUrl`): «дані про стан платежу надсилаються при зміні статусу, **окрім статусу
`expired`**». `failure` (відхилена картка) приходить і вже обробляється.

**Наслідок** Непроплачений інвойс лишався б `pending` назавжди, а
`create_pending_payment` (міграція 0044) рахує pending-платежі як зарезервований
реферальний кредит.

**Що зроблено** Інвойси створюються з `validity = 24 год`; щоденний cron
`/api/billing/renew` (`expireAbandonedCheckouts`) закриває як `failed` інтерактивні
платежі без `subscription_id`, що висять `pending` понад 25 год. Резерв кредиту в
`create_pending_payment` додатково обмежений 48 годинами як фолбек, якщо cron не
відпрацює. Renewal-платежі (з `subscription_id`) сюди не потрапляють — їх розв'язує
`lookupCharge` через statement.

**Коли переглянути** Якщо Monobank почне надсилати webhook для `expired` — прибрати
sweep (він стане no-op, шкоди не буде).

## Пробний період сайту: 7 днів у застосунку проти 30 днів у базі

*Записано 26.09.2026 · статус: відкладено, не виправляти*

**Що не збігається**
- Застосунок: `SITE_TRIAL_DAYS = 7` у `src/lib/plans.ts`. На цьому числі
  працюють `isSiteTrialExpired` / `siteTrialDaysLeft` (сторінка сайту в
  кабінеті, заборона публікації в `src/lib/actions/site.ts`) і тексти
  «Пробний період — 7 днів», «1 сайт на 7 днів» (`src/lib/landing/copy.ts`,
  `src/lib/i18n/dictionaries/uk.ts`).
- База: `supabase/migrations/0025_site_trial_expiry.sql` рахує
  `interval '30 days'` у трьох місцях — `get_site`,
  `get_published_site_handles` (приховування сайту й випадіння з sitemap) та
  `expire_trial_sites()` (щоденне зняття з публікації). Пізніші міграції це
  не змінювали.

**Наслідок**
Після 7-го дня кабінет показує пробний період як закінчений і не дає
опублікувати сайт, але вже опублікований сайт лишається доступним публічно
до 30-го дня.

**Чому не виправляємо**
Сайт-візитку фотографа планується прибрати, пробний період зникне разом із
нею. Вирівнювати SQL заради продукту, що йде, немає сенсу.

**Коли закрити**
Під час видалення сайтів: прибрати `SITE_TRIAL_DAYS`, `isSiteTrialExpired`,
`siteTrialDaysLeft`, умови `site_trial` в SQL-функціях з `0025` та
`expire_trial_sites()`. Якщо рішення про видалення скасують — вирівняти
`0025` під 7 днів новою міграцією (або константу під 30) і звірити тексти.
